# Toolchain Integration Roadmap and Test Harness

> **Worked example.** This is one project's roadmap, kept as written on 2026-11-07. In this kit, the runner is `skills/integrate/scripts/toolchain_harness.py` and this project's suite is `examples/attack-first/suite.json`. Use the generic procedure in `skills/integrate/SKILL.md` for new projects. Its adapters are not implemented, so running this suite fails closed.

This report turns the earlier Attack First/Hermes discussion into a sequential integration plan: add one component, prove its behavior with controlled synthetic tasks, run a representative job, then approve the next component. The deliverable includes an executable contract-test runner, machine-readable fixtures, and six job templates; it does not claim that the vendor adapters or production integrations already exist.

Prepared November 7, 2026. All rollout policies, thresholds, schemas, and example data below are proposed engineering contracts, not established product requirements or vendor defaults.

## Scope and recommendation

Use the six components discussed previously: Hermes/Langfuse tracing, DeepEval trajectory evaluation, allpairspy schedule-CSV coverage, TrackEval tracking evaluation, scikit-learn coach agreement with optional prevalence correction, and a local failure-harvesting component. Keep the team-management MVP and the experimental basketball-video workflow separate: a tracking regression must not become an unrelated schedule-import release blocker.

- **Start now:** Establish the common result contract, then integrate tracing with synthetic content only.
- **Next:** Add trajectory checks and schedule-CSV fixtures, one at a time. This is the minimum useful app-development slice.
- **Later:** Add tracking and agreement checks only for the video experiment, then failure harvesting across whichever stages are enabled.
- **No forced dependency:** Tracking does not technically depend on CSV parsing. Their rollout order limits simultaneous change, not the runtime dependency graph.
- **Explicit deferral:** If video work is deferred, record that decision and move from CSV to failure harvesting. Do not label unimplemented video stages as passing.

## Sequential rollout and promotion gates

Treat each row as a separate integration change with a named implementer and reviewer assigned before work starts. Use completion gates rather than calendar promises; no stage is approved solely because installation succeeded.

| Order | Component introduced | Integration boundary | Synthetic acceptance | Representative job | Promotion and rollback |
|---|---|---|---|---|---|
| Foundation | Common contract and runner | One JSON request in, one JSON result out | Runner self-tests; no empty test selection; malformed results rejected | Local contract smoke test | Freeze schema v1; revert runner independently of adapters |
| Tracing | Hermes/Langfuse adapter | Observer events to redacted export plus coverage result | `TRACE-*`, including outage and leak controls | Summarize one completed UTC day's traces | Verify delivery, correlation, and privacy; disable observer export on regression, never bypass release evidence checks |
| Trajectory | DeepEval adapter plus local policy checks | Trace to bounded workflow verdict | `TRAJ-*`, including skipped tests, looping, forbidden tool, failed outcome | Evaluate one development run bound to a commit | Require both procedural and outcome evidence; revert adapter version, retain last approved policy |
| CSV | allpairspy generator plus app parser adapter | Generated bytes to normalized events or structured rejection | `CSV-*`; complete pair coverage and zero output mismatches | Validate one schedule import in dry-run mode | Freeze reviewed fixture manifest; revert parser change if golden outputs change unexpectedly |
| Tracking | TrackEval adapter | Synthetic tracks or approved labeled clips to normalized metrics | `TRACK-*`; perfect, ID swap, dropout, malformed frame | Score one candidate tracker against one approved baseline | Require separate video approval; disable candidate tracking release, not unrelated MVP releases |
| Agreement | scikit-learn adapter and optional correction | Paired labels to agreement and calibration report | `AGREE-*`; exact matrix calculations and undefined cases | Compare two coach exports for one event type | Approve labeling rubric before model threshold tuning; retain prior rubric and labels on regression |
| Harvest | Local review-queue adapter | Failed evidence to scrubbed, deduplicated pending cases | `HARVEST-*`; deduplication, privacy, approval denial | Collect failures into a human review queue | No automatic golden promotion; rollback queue writer without changing approved goldens |

### Repeatable gate for every component

1. Record adapter commit, package versions, host, configuration hash, and fixture-manifest hash. Install only that stage's new dependency in an isolated environment.
2. Implement the adapter and run the stage's positive, negative, and error fixtures. A correct rejection is a passing test, not a passing product result.
3. Run all previously enabled stages' regression suites. Do not execute future stages simply to make an overall dashboard green.
4. Run the stage's representative job twice with independent run directories and the same approved inputs. Require matching deterministic outputs and no duplicated side effects; timestamps and run IDs may differ.
5. Have a reviewer inspect the artifacts and approve the pinned component. Missing cases, timeouts, malformed responses, stale evidence, or unexplained differences stop promotion.
6. Save the rollback target and then unlock the next component. Two clean jobs establish repeatability on those inputs, not production reliability or statistical confidence.

For app release, require the repository's normal unit/integration tests and permission tests in addition to these evaluation checks. In particular, the existing requirement that children cannot send messages or receive DMs needs backend authorization tests; a good agent trajectory is not evidence of correct permissions.

## Shared harness contract

### File layout

Keep the delivered files together at first. When integrating them into a repository, preserve the suite-relative adapter paths or update the adapter map explicitly.

```text
evals/
  toolchain_harness.py
  toolchain_synthetic_suite.json
  adapters/
    tracing.py
    trajectory.py
    csv.py
    tracking.py
    agreement.py
    harvest.py
  jobs/
    trace-summary.json
    trajectory-review.json
    schedule-dry-run.json
    tracking-regression.json
    coach-agreement.json
    harvest-failures.json
  fixtures/                 # reviewed, versioned; agent cannot approve changes
  policies/                 # reviewed policies and thresholds
  evidence/run-<unique>/    # append-only run directories
  harvest/pending/          # proposed cases only
```

The `adapters/`, fixture, policy, and job directories above are the proposed integration layout, not directories already populated by this deliverable. The runner creates evidence directories; adapters must write their output artifacts only inside the `output_dir` supplied for that invocation.

### Request and response

The runner invokes a configured argv list without a shell, sends the following JSON on stdin, and expects exactly one JSON document on stdout. Vendor logs belong on stderr, which the runner does not copy into its result report.

```json
{
  "schema_version": "1",
  "case_id": "TRAJ-OK",
  "fixture_sha256": "<runner-computed SHA-256 of canonical input JSON>",
  "input": {
    "mode": "synthetic",
    "policy": "exact",
    "expected": ["read_file", "edit_file", "run_tests"],
    "actual": ["read_file", "edit_file", "run_tests"],
    "max_calls": 3,
    "tests_exit": 0
  },
  "output_dir": "<runner-created absolute directory>"
}
```

```json
{
  "schema_version": "1",
  "case_id": "TRAJ-OK",
  "fixture_sha256": "<echo the request binding>",
  "status": "pass",
  "summary": "Required workflow completed and outcome checks passed.",
  "reason_codes": [],
  "metrics": {
    "exact_match": true,
    "deepeval_score": 1.0,
    "tool_calls": 3
  },
  "artifacts": ["trajectory-evidence.json"],
  "next_actions": []
}
```

Artifact paths must be relative to `output_dir`, stay inside it after path resolution, and refer to existing files. The runner saves each validated response as `_adapter-result.json` and the run index as `results.json`; adapters must reserve that result filename and sanitize their metrics, summaries, and artifacts before returning.

Echoing the request hash binds the response to the fixture but does not prove the tool actually ran. Live qualification additionally requires vendor evidence, adapter/version provenance, and reviewer inspection.

| Adapter status | Adapter exit | Meaning | Promotion result |
|---|---:|---|---|
| `pass` | 0 | Required checks were completed and accepted | Eligible for review |
| `block` | 1 | Valid evaluation found a policy violation or unacceptable result | Stop |
| `error` | 2 | Evidence unavailable, malformed input, undefined metric, or execution failure | Stop |

The harness exits 0 only when every selected synthetic case produced its expected status, exit code, and assertions. It exits 1 for assertion mismatches and 2 for protocol/execution errors; in `--job` mode it propagates the live adapter's valid status exit, so an expected-error fixture cannot accidentally authorize a live job.

### Run commands

These commands run immediately for the runner self-test. Stage and live-job commands require the corresponding adapters; absent adapters correctly return an error rather than a fabricated success.

```bash
# Runner verification only; no external services or credentials.
python toolchain_harness.py --self-test

# Run one stage after its adapter has been implemented.
python toolchain_harness.py toolchain_synthetic_suite.json --stage tracing
python toolchain_harness.py toolchain_synthetic_suite.json --stage trajectory
python toolchain_harness.py toolchain_synthetic_suite.json --stage csv

# Run all six acceptance sets only after all six adapters exist.
python toolchain_harness.py toolchain_synthetic_suite.json

# Execute a representative live job after saving its template below.
python toolchain_harness.py toolchain_synthetic_suite.json \
  --job jobs/schedule-dry-run.json
```

The runner is not an operating-system sandbox and does not enforce network or application permissions. It inherits the caller's environment, and its subprocess timeout is not a process-tree resource limit; run adapters in a separate restricted environment, deny unnecessary credentials/network access, and prevent arbitrary child processes before production adoption.

## Synthetic acceptance tasks

The companion JSON contains the full machine-readable inputs and assertions for every case below. An adapter must compute from those inputs and call the appropriate pinned component, not recognize a case ID and return a canned answer.

### Tracing: prove visibility without leaking content

The current Hermes catalog documents a per-profile Langfuse installation, one trace per turn, one generation per API call, and one observation per tool call; it also documents fail-open observer behavior and possible telemetry loss rather than an offline spool ([Hermes plugin documentation](https://hermes-agent.nousresearch.com/docs/plugins/langfuse)). Therefore use an independent completeness check and never treat observer success as release authorization.

Start with `metadata` capture and synthetic content; the plugin's default `sanitized` mode redacts secret patterns but is explicitly not a DLP guarantee, and opt-in end-user attribution can export unhashed platform IDs ([Hermes capture and attribution documentation](https://hermes-agent.nousresearch.com/docs/plugins/langfuse)). Keep that attribution disabled and test all metadata fields, not just prompt content.

| Case | Task and expected input | Expected output |
|---|---|---|
| `TRACE-OK` | Feed a fixed synthetic observer sequence: one turn, one generation, three tool calls, 100 input and 20 output tokens; fake email, fake secret marker, and fake signed URL | `pass/0`; counts 1/1/3; 120 total tokens; correlation complete; zero canary leaks; unknown cost remains `null` |
| `TRACE-MISSING` | Start a fresh isolated process with both Hermes-prefixed and SDK credential aliases absent; execute the same agent action | `error/2`, `TRACE_MISSING`; agent completes; zero traces received by the 30-second fixture deadline |
| `TRACE-LEAK` | Supply an export containing the fake email inside nested metadata | `block/1`, `PRIVACY_CANARY`; exactly one canary leak |

The one-generation shape is a controlled event fixture, not a promise about how many model calls a real coding task will make. Use full sampling for this qualification, wait within a bounded delivery deadline, and scan the actual serialized export and persisted artifacts rather than trusting a `redacted=true` flag.

If content export is later required, verify the actual plugin/SDK masking extension rather than assuming a callback can be added through an environment variable. Langfuse documents different masking paths and notes that masking in one client does not protect another exporter ([Langfuse masking documentation](https://langfuse.com/docs/observability/features/masking)).

### Trajectory: prove the procedure and the result

DeepEval documents deterministic tool comparison, optional argument/output comparison, and exact-match semantics; passing `available_tools` adds a separate tool-selection evaluation, so omit it from this initial deterministic gate ([DeepEval Tool Correctness](https://deepeval.com/docs/metrics-tool-correctness)). Keep local step-budget, forbidden-action, and outcome checks independent of a library score.

Use exact sequence checks only for a verified wrapper with a fixed procedure. For open-ended feature development, use an outcome policy with required evidence and forbidden actions instead of demanding one canonical tool-call order.

| Case | Input | Expected output |
|---|---|---|
| `TRAJ-OK` | Expected and actual `[read_file, edit_file, run_tests]`; maximum 3 calls; test exit 0 | `pass/0`; exact match true; DeepEval score 1.0; 3 calls |
| `TRAJ-LOOP` | Six extra reads before the three-call workflow, for 9 total calls | `block/1`, `STEP_BUDGET`; report 9 calls |
| `TRAJ-SKIP` | Actual `[read_file, edit_file]`; no test result | `block/1`, `REQUIRED_TOOL_MISSING` |
| `TRAJ-TEST-FAIL` | Exact workflow, but `run_tests` exits 1 | `block/1`, `OUTCOME_FAILED` |
| `TRAJ-FORBIDDEN` | Outcome-mode run calls `run_tests` then forbidden `send_message` | `block/1`, `FORBIDDEN_TOOL`, even though tests passed |

Do not assert a guessed score for the repeated-read case. The explicit call budget already establishes the intended behavior without depending on changing library treatment of repeated names.

For live runs, bind the trace, test output, policy, and candidate commit in a single manifest. Reject a trace from another commit or a test result produced before the final edit; tool names alone cannot prove that the right files were tested.

### CSV: prove pair coverage and parser outcomes

allpairspy provides `AllPairs(parameters)` and optional filtering, with filters that may receive incomplete combinations; its documentation does not promise a minimal test set ([allpairspy documentation](https://github.com/thombashi/allpairspy/)). Generate first, then independently verify coverage instead of promising a fixed number of files.

For this fixture contract, use seven columns: `event_id,date,start_time,end_time,event_type,location,notes`. Dates must be valid ISO calendar dates, times use `HH:MM`, event type is `game` or `practice`, and notes may be blank; this is a proposed test schema to reconcile with the actual app parser before promotion.

| Dimension | Values |
|---|---|
| Event type | `game`, `practice` |
| Notes | empty, `Bring water` |
| Line endings | LF, CRLF |
| Location | `Gym`, `Gym, North` |
| UTF-8 BOM | absent, present |

These five binary dimensions produce 32 exhaustive combinations and 40 distinct pair requirements, calculated as \(\binom{5}{2}\times 2\times 2\). No constraints are imposed in this synthetic matrix, so every pair must appear in the generated set.

| Case | Input | Expected output |
|---|---|---|
| `CSV-PAIRWISE` | Generate the dimensions above using allpairspy; parse every emitted CSV through the app parser | `pass/0`; required pairs 40, covered pairs 40, zero normalized-output mismatches; 1–32 fixtures |
| `CSV-QUOTED` | One CRLF row with `"Gym, North"` and blank notes | `pass/0`; one exact normalized row, with the comma retained inside the location |
| `CSV-SHORT-ROW` | A five-field row under the seven-field header | `block/1`, `CSV_COLUMN_COUNT`; line 2; zero writes |
| `CSV-BAD-DATE` | Date `2026-02-30` | `block/1`, `CSV_DATE`; zero writes |
| `CSV-EMPTY` | Header with no event rows | `block/1`, `NO_EVENTS` |

The human-readable short-row error should be “Line 2: expected 7 columns, found 5.” Generate expected parsed objects from the fixture definitions, not by reusing the parser being tested; freeze fixture hashes under review and keep generation out of ordinary PR acceptance.

### Tracking: distinguish identity errors from missed detections

TrackEval implements HOTA and identity metrics and supports custom benchmarks through dataset conversion or a dataset adapter ([TrackEval documentation](https://github.com/JonathonLuiten/TrackEval)). This stage evaluates tracking only; it does not validate paint-touch recognition or turn candidate clips into verified event counts.

Define `two-nonoverlapping-tracks-v1` as frames 1–300 with two boxes per frame: ID 1 at `(10+f,10,20,40)` and ID 2 at `(500-f,100,20,40)`, where `f` is the frame number. Use a 640×200 image and 30 FPS; the separate vertical positions ensure zero cross-player overlap and make the expected association outcomes unambiguous.

Use explicit field mapping rather than copying a tracker submission into GT. The MOTChallenge format guide describes one-based frame/ID indexing and ten-field submissions, while TrackEval's actual MOT loader separately reads GT marking/class columns and tracker confidence ([MOTChallenge format guide](https://github.com/JonathonLuiten/TrackEval/blob/master/docs/MOTChallenge-format.txt), [TrackEval loader](https://github.com/JonathonLuiten/TrackEval/blob/master/trackeval/datasets/mot_challenge_2d_box.py)).

```text
# Proposed GT representation: frame,id,x,y,w,h,active,class,visibility
1,1,11,10,20,40,1,1,1

# Tracker representation: frame,id,x,y,w,h,confidence,x_world,y_world,z_world
1,1,11,10,20,40,1,-1,-1,-1
```

Require the adapter to validate sequence metadata, frame range, unique `(frame,id)` pairs, and positive box dimensions before evaluation. Pin the dataset loader configuration, set pedestrian GT class explicitly, and document any disabled preprocessing rather than relying on folder-name defaults.

Normalize reported ratios to `[0,1]` with explicit source units; do not infer units from whether a number happens to exceed 1. The expected values below are analytic fixture oracles derived from TrackEval's association counts and \(\mathrm{HOTA}=\sqrt{\mathrm{DetA}\cdot\mathrm{AssA}}\), not results of a vendor integration run in this deliverable ([TrackEval HOTA implementation](https://github.com/JonathonLuiten/TrackEval/blob/master/trackeval/metrics/hota.py)).

| Case | Controlled fault | Expected normalized output, tolerance \(10^{-6}\) |
|---|---|---|
| `TRACK-PERFECT` | None; tracker matches GT | `pass/0`; HOTA=1, IDF1=1, DetA=1, AssA=1 |
| `TRACK-SWAP` | Swap IDs from frame 151 onward; boxes unchanged | `block/1`, `TRACKING_REGRESSION`; DetA=1, AssA=1/3, HOTA≈0.5773502692, IDF1=0.5 |
| `TRACK-DROP` | Remove both tracks on frames 100–130 inclusive, then resume original IDs | `block/1`, `TRACKING_REGRESSION`; DetA=AssA=HOTA=269/300≈0.8966666667; IDF1=538/569≈0.9455184534 |
| `TRACK-FRAME-ZERO` | Inject a frame-zero row | `error/2`, `TRACK_FORMAT`; do not compute a score |

The synthetic gate requires perfect tracking on this deliberately easy fixture. Real-video thresholds must be set from reviewed, representative data and kept separate; this fixture also corrects the earlier suggestion that association accuracy necessarily remains unchanged during a dropout.

### Agreement: prove the rubric is measurable

scikit-learn defines Cohen's kappa as observed agreement corrected for expected agreement under the annotators' label marginals, and documents undefined cases ([scikit-learn kappa documentation](https://scikit-learn.org/stable/modules/generated/sklearn.metrics.cohen_kappa_score.html)). Return `null` plus an error reason for an undefined result, never a passing replacement value.

Each synthetic confusion matrix has annotator A as rows and B as columns, with negative then positive class order. Expand each matrix into aligned label pairs for the library call; live exports must join on unique window IDs and matching rubric versions rather than file row position.

| Case | Input | Expected output |
|---|---|---|
| `AGREE-HIGH` | `[[48,2],[3,47]]`, N=100 | `pass/0`; raw agreement 0.95, kappa 0.90 |
| `AGREE-SKEW` | `[[60,20],[20,0]]`, N=100 | `block/1`, `LOW_AGREEMENT`; raw agreement 0.60, kappa −0.25 |
| `AGREE-UNDEFINED` | `[[100,0],[0,0]]` | `error/2`, `KAPPA_UNDEFINED`; kappa `null` |
| `AGREE-CORRECTION` | Observed positive rate 0.41, sensitivity 0.90, specificity 0.80 | `pass/0`; corrected prevalence 0.30 |
| `AGREE-DEGENERATE` | Sensitivity=0.50, specificity=0.50 | `error/2`, `CALIBRATION_UNIDENTIFIABLE`; corrected prevalence `null` |

Use kappa ≥0.80 and N≥100 only as proposed review triggers, not universal proof of acceptable labels. Report raw agreement, class balance, N, and exclusions alongside kappa; missing IDs, duplicate IDs, mixed rubric versions, or insufficient pairs must stop the live job.

The optional Rogan–Gladen correction is \((p_{\mathrm{observed}}+\mathrm{specificity}-1)/(\mathrm{sensitivity}+\mathrm{specificity}-1)\); its validity depends on applicable sensitivity/specificity estimates, and incompatible inputs can yield values outside `[0,1]` ([Rogan–Gladen explanation](https://pmc.ncbi.nlm.nih.gov/articles/PMC7619182/)). Reject invalid or near-zero-denominator calibration, flag out-of-range estimates rather than silently clipping, and never use an aggregate correction to claim a particular athlete performed a particular event.

### Harvesting: convert failures into reviewable candidates

Use a local allowlisted record format, not raw logs copied into a dataset. Preserve only stage, sorted reason codes, policy version, sanitized normalized input, provenance references, and occurrence IDs; drop unapproved content fields before storage.

Define the exact deduplication key as SHA-256 over canonical JSON of `(stage, reason_codes, policy_version, normalized_input)` after sanitation. Exclude timestamps and run IDs from identity but retain them as occurrences; compare canonical content on hash matches and replay occurrence IDs idempotently.

| Case | Input | Expected output |
|---|---|---|
| `HARVEST-DEDUP` | Two identical semantic failures with different timestamps/run IDs, plus one distinct failure; ingest the same set twice | `pass/0`; 2 pending cases, 3 occurrences, zero new cases on second ingest, zero promotions |
| `HARVEST-SECRET` | One failure with fake API-key and email values in disallowed debug fields | `pass/0`; 1 pending case; zero canaries in persisted outputs; zero promotions |
| `HARVEST-NO-APPROVAL` | Promotion request with no reviewer authorization | `block/1`, `APPROVAL_REQUIRED`; zero promotions |
| `HARVEST-UNSAFE` | Unconsented media reference outside the allowed root | `block/1`, `UNSAFE_INPUT`; zero pending cases; do not open the path |

Near-duplicate similarity is a later review aid, not an automatic deletion rule. Do not deduplicate distinct failures merely because their traces look similar, and do not assume stripping metadata anonymizes visible people in video.

Promote a pending case only through a reviewed change that records the approved oracle, owner, consent/retention status where relevant, and dataset split. Keep tuning cases separate from held-out evaluation cases, and never let the same coding agent both change an oracle and approve its own result.

## Clean sample job templates

These are proposed job inputs for this runner, not Hermes cron syntax or vendor-native configuration files. Save each as the indicated JSON file, implement the corresponding `mode: live` adapter handler, and run it with `--job`; all input paths below are resolved relative to the suite directory and must remain inside approved roots.

No scheduler, publisher, or external writer is enabled by these templates. Initially run jobs manually; if scheduling is added later, require a lock against concurrent runs, explicit timezone/profile selection, bounded retries, and idempotent output handling.

Any unexplained missing session returns `error/2`; explicitly empty expected activity is recorded as no activity, not evidence of tracing health.

Expected flow: validate IDs/rubric → align paired windows → compute confusion matrix, agreement, and kappa → list disagreements for human review. Do not silently discard unmatched rows; correction remains off until a separately approved calibration dataset exists.

### Failure harvesting

Save as `jobs/harvest-failures.json`. This creates a proposed queue update inside the run's output directory; it cannot directly mutate approved goldens or a shared review queue.

```json
{
  "schema_version": "1",
  "id": "harvest-failures-review-batch",
  "stage": "harvest",
  "timeout_s": 120,
  "input": {
    "mode": "live",
    "operation": "prepare-pending-batch",
    "failure_manifest": "fixtures/failures/review-batch.json",
    "existing_pending_index": "harvest/pending/index.json",
    "deduplication": "canonical-sha256-v1",
    "sanitize_before_hash": true,
    "include_raw_media": false,
    "auto_promote": false,
    "outputs": ["pending-batch.json", "pending-index-proposed.json", "review-queue.md"]
  }
}
```

Expected flow: authorized failure manifest → allowlist/sanitize → compare against existing index → merge occurrences in a proposed index → review queue artifacts. A separate reviewer applies the update; persisting that merge must use locking or compare-and-swap so concurrent runs cannot lose cases.

## Typical end-to-end usage

### App-development change

Use the tracing, trajectory, CSV, and harvesting components for a schedule-parser change. Do not introduce the video stack into this path.

1. A developer approves the task, repository boundary, and allowed tools, then starts a trace-bound Hermes run.
2. Hermes edits the parser and runs the app tests. The local run manifest records the final commit and test artifacts.
3. CI executes the frozen CSV fixtures and the trajectory-review job against that exact commit. Missing evidence or failed outcomes block advancement.
4. A schedule dry-run job turns a sample CSV into a preview, with no database writes.
5. Failures become proposed pending cases. A human reviews the change and any new fixtures; only the existing release process can merge or deploy.

The successful result is a reviewed code change with reproducible parser outputs and attached execution evidence. It is not merely a high trajectory score or a populated trace dashboard.

### Video-model experiment

Use tracking, agreement, and harvesting as a distinct evaluation path, with tracing only where an agent is actually used. Labels and footage must be approved before they enter the workflow.

1. Freeze the clip/window manifest and rubric. Have two coaches label independently.
2. Run the agreement job; resolve rubric ambiguity before tuning on disagreements.
3. Evaluate candidate and baseline tracks on the same held-out sequences, then review per-sequence errors.
4. If the experiment includes paint-touch retrieval, separately measure retrieval recall/precision against reviewed window labels; HOTA does not substitute for that task-specific evaluation.
5. Harvest approved failure summaries into pending review without copying raw youth footage or promoting cases automatically.

The successful result is a bounded experiment report with a known dataset and error categories. Candidate similarity scores, tracking metrics, and corrected prevalence estimates remain distinct from verified athlete event counts.
